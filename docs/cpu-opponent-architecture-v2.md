# MonsterMazeEngine CPU Opponent Architecture v2

## Role

MonsterMazeEngine is the high-throughput development and training environment for the Monster Maze CPU-opponent system.

It is not the production server and it is not the final AI runtime.

Its primary job is to make millions of controlled, source-faithful experiments cheap.

```
MonsterMaze 1.8
  authoritative live game
        ^
        | differential validation
        |
MonsterMazeEngine
  fast offline world
        |
        v
MonsterMazeAI training
```

## Responsibilities

Engine owns:

- deterministic 1.8 mechanics simulation;
- seeded monster/pad/game randomness;
- state/action stepping;
- batched rollout generation;
- replay and trace comparison;
- teacher/search evaluation;
- policy benchmarking;
- profile-conditioned evaluation.

Engine does not own:

- Bukkit/NMS server integration;
- production CPU avatar code;
- final player presentation;
- Discord/backend features;
- the Python training loop.

## Single semantic contract

The engine's `GameState` and `Action` must be the executable form of the shared CPU semantic contract.

The same contract defines:

- units;
- coordinate conventions;
- timing;
- action ranges;
- profile fields;
- event semantics;
- terminal conditions.

Compatibility must be tested rather than inferred from similar field names.

## Simulation loop

```
initial state
    |
policy / teacher
    |
Action
    |
Engine.tick
    |
next state + events
    |
repeat
```

The simulation must be deterministic for:

```
layout
mode
kit
seed
initial state
action sequence
```

and must preserve stochastic behaviour through explicit seeded random streams.

## Runtime and training must use different performance modes

### Training mode

May use:

- many parallel environments;
- full world state;
- repeated search;
- Monte Carlo evaluation;
- detailed event traces;
- allocation-heavy debugging.

### Policy/runtime evaluation mode

Must mimic the production server:

- same compact policy features;
- same profile conditioning;
- same model artifact;
- no teacher/search assistance;
- measured per-agent inference time.

This prevents a benchmark from claiming that the learned policy is successful when the success actually comes from a hidden planner.

## Hierarchical policy support

The engine should support two policy calls:

### Strategic

Called on pad transition or a small cadence.

Output is a tactical intent:

- target objective/route family;
- risk level;
- monster interaction preference;
- ability intent;
- competitor interaction posture.

### Locomotion

Called each tick.

Consumes:

- current physical state;
- tactical intent;
- profile;
- local threats.

Outputs the per-tick action.

The engine itself remains the authoritative physics executor.

## Teacher/search layer

The current planning machinery should be treated as an offline teacher.

Its job is to answer:

> From this exact simulated state, which source-valid action or short trajectory has the strongest expected outcome?

It can use expensive search because it never runs inside the production server.

Teacher outputs should be stored as labelled training examples.

This creates a clean transition path:

```
heuristic/search intelligence
       |
       v
teacher trajectories
       |
       v
learned policy
       |
       v
cheap server runtime
```

## DAgger/search-distillation support

Engine must be able to take states generated by a candidate policy and ask the teacher to improve selected states.

The minimum offline loop is:

1. start with a policy;
2. run the policy in Engine;
3. sample difficult/novel states;
4. run teacher search from those states;
5. store improved first actions;
6. retrain;
7. compare against holdout;
8. repeat.

This lets the policy improve specifically on the states where it fails rather than requiring another hand-written controller.

## Profile-conditioned simulation

Engine must sample profiles across the intended configuration space.

Profiles contain capability and tendency values.

The mechanics cannot be modified by a profile.

A low-skill player must fail or choose differently through the policy's decisions; the engine must not secretly reduce gravity, speed, collision range, health, or other game mechanics.

## Multi-player training

Engine should support several participants in one simulation.

Each participant has:

- independent player state;
- independent profile;
- independent policy state/seed.

The shared world contains:

- one maze;
- one monster population;
- active/preview/old pads;
- all participant positions and progress.

This is required for the eventual CPU-vs-human/CPU race objective.

## Efficient rollout architecture

The engine should eventually expose a batched rollout API in addition to the one-tick API.

Conceptually:

```
Batch
  Environment 0
  Environment 1
  ...
  Environment N
       |
       v
compact observations
       |
       v
policy batch inference
       |
       v
actions
       |
       v
Engine ticks
```

This reduces overhead when large numbers of training environments are running.

It also permits the Python trainer to operate on batches rather than one Java process call per tick.

The first implementation can retain the scalar API and add batching after profiling confirms the need.

## State allocation rules

The current engine can remain easy to debug, but high-volume training should provide a reusable-state mode.

Goals:

- avoid deep-copying a 99x99 maze every tick;
- reuse player/monster buffers;
- reuse action/observation arrays;
- preallocate event buffers;
- keep static maze topology immutable;
- separate dynamic world state from static layout data.

The current `GameState.copy()` path is suitable for correctness tests but must not become a hidden bottleneck for millions of episodes.

## Static precomputation

For each fixed maze layout, cache:

- graph adjacency;
- physical-floor masks;
- valid route families;
- gap transitions;
- pad candidate regions;
- coordinate conversions.

The fixed layout should not be recomputed per bot or per environment tick.

## Dynamic threat handling

Monster and player queries should use compact local indexes.

A rollout should not repeatedly scan every monster for every policy feature when a spatial index can provide the local candidates.

The full monster population remains in the simulation because distant actors can become relevant later.

Local filtering is a feature/inference optimisation, not a mechanic change.

## Evaluation matrix

The engine must support full evaluation without an arbitrary stage ceiling.

Dimensions include:

- pattern;
- mode;
- kit;
- difficulty/profile;
- seed.

Each result retains:

- final stage;
- terminal reason;
- time;
- damage;
- ability usage;
- profile;
- model version;
- inference cost.

A stage-limited smoke test may exist for CI, but it must never be confused with the full capability matrix.

## Differential validation

The most important engine validation is comparison with MonsterMaze 1.8.

Use deterministic traces where possible:

```
initial state
+ action sequence
        |
        +--> Engine trace
        |
        +--> 1.8 trace
        |
        v
field-by-field comparison
```

When a difference occurs, classify it as:

- contract mismatch;
- engine bug;
- 1.8 implementation behaviour;
- observation uncertainty.

Do not "fix" the engine by tuning the AI to compensate for a mechanics mismatch.

## Model artifact compatibility

The same policy artifact exported by MonsterMazeAI must be loadable by Engine without conversion that changes semantics.

Engine should validate:

- model schema;
- feature names/order;
- profile vector order;
- normalization;
- action heads;
- checksum.

Engine's policy inference should be dependency-free and numerically stable.

## Engine UI

The Swing playable engine remains useful as a visual validation tool.

It is not part of the high-throughput training path.

The UI should be able to load a policy artifact and a profile so we can visually inspect:

- route intent;
- movement;
- monster interactions;
- abilities;
- competitor behaviour.

## Success gates

The redesigned Engine is successful when it can:

1. run the source-faithful mechanics independently;
2. load the same policy artifact intended for the 1.8 server;
3. execute the policy without teacher assistance;
4. run many seeds reproducibly;
5. generate training trajectories quickly enough to make continuous local training practical;
6. support multi-player episodes;
7. produce the full matrix with no permanent stage cap;
8. emit traces suitable for differential comparison with Minecraft 1.8.

## Non-goals

Engine should not grow into another production game implementation with independent gameplay rules.

When a mechanic is corrected, the change must be justified against MonsterMaze evidence/source and accompanied by differential tests.

The objective is not to create the smartest possible search controller here. The objective is to make the true CPU policy trainable and measurable.


## Exact-state training, player-equivalent observation

Engine has access to complete simulated state, just as MonsterMaze has complete authoritative state.

Training should generate the **same compact observation** that the production server exposes to the CPU brain.

Do not train the production policy directly on privileged simulator fields such as hidden future pad state, distant monsters or arbitrary future trajectory knowledge unless those fields are deliberately part of the configured CPU awareness model.

This prevents the common failure mode where the simulator policy looks strong but cannot be deployed under the real runtime information contract.

## Route catalogue

Because the game has a small number of fixed maze patterns, static route data should be precomputed once and reused by all environments.

A route catalogue contains physical route families, gap/corner metadata and route costs.

Training may additionally use expensive search to produce better labels; the catalogue itself remains lightweight and deterministic.

## Simulation throughput

A correct scalar Engine tick remains the reference implementation.

High-volume training should use reusable mutable state, static shared maze data and batched policy inference.

The 99x99 maze should never be deep-copied as part of an ordinary policy step.
